# Ushqyr AI Bench: протокол обмена, версия 1

На этом протоколе работает Python SDK (`bench/sdk/python`). Он записан для того, чтобы клиент можно было написать на
любом языке. Протокол охватывает синхронный режим, режим реального времени и все датчики. Номер версии повышается,
только если меняется существующее сообщение.

## Транспорт

- TCP. Симулятор слушает порт **5757** (поле `port` в файле правил или `-bench-port`), только на этом компьютере,
  если он не запущен с `-bench-listen-all`.
- Одна программа одновременно. Новое соединение заменяет старое.
- На клиенте отключите алгоритм Нейгла (`TCP_NODELAY`).

## Кадр

В обе стороны идет один и тот же кадр. Все целые числа записаны младшим байтом вперед (little-endian).

| Байты | Поле | Что это |
|---|---|---|
| 4 | `length` | Число байт, которые идут дальше (тип + длина заголовка + заголовок + данные) |
| 1 | `type` | Номер сообщения, см. ниже |
| 4 | `header_length` | Размер заголовка |
| `header_length` | `header` | Словарь [MessagePack](https://msgpack.org) со строковыми ключами |
| остальное | `payload` | Сырые байты; их раскладку описывает заголовок |

Пределы того, что принимает симулятор: кадр не больше **16 КиБ**, вложенность заголовка не больше 8 уровней, не
больше 256 элементов в словаре или массиве, строки не длиннее 4096 байт. Кадр, который нарушает предел, заголовок,
который не является словарем, или больше 64 сообщений без ответа закрывают соединение.

## Сообщения

| № | Название | Направление | Тренировка | Соревнование |
|---|---|---|---|---|
| 1 | `HELLO` | программа → симулятор | да | да |
| 2 | `START` | программа → симулятор | да | да, один раз |
| 3 | `STEP` | программа → симулятор | да | да |
| 4 | `RESET` | программа → симулятор | да | **нет** |
| 5 | `DONE` | программа → симулятор | да | да |
| 6 | `PING` | программа → симулятор | да | **нет** |
| 129 | `WELCOME` | симулятор → программа | | |
| 130 | `OBSERVATION` | симулятор → программа | | |
| 131 | `PONG` | симулятор → программа | | |
| 132 | `ERROR` | симулятор → программа | | |

На сообщение, которое режим не разрешает, на неизвестный номер сообщения и на все, что пришло до `HELLO`, симулятор
отвечает `ERROR` и закрывает соединение. Режим задает симулятор. Программа не может его сменить ничем из того, что
отправляет.

### HELLO → WELCOME

Заголовок `HELLO`:

| Ключ | Тип | Что это |
|---|---|---|
| `proto` | int | Должен быть `1` |
| `token` | str | Должен совпадать с токеном симулятора, если токен задан |
| `client` | str | Произвольный текст для журнала симулятора |
| `truth` | bool | Только тренировка: добавлять в каждое наблюдение истинные координаты |
| `pace` | bool | Только тренировка: `false` разрешает симуляции идти так быстро, как может компьютер |

Заголовок `WELCOME`:

| Ключ | Что это |
|---|---|
| `proto` | `1` |
| `mode` | `"training"` или `"competition"` |
| `track` | Только тренировка: `id` и `hash` загруженного файла трассы. В режиме соревнования не отправляется никогда |
| `sim` | Версия симулятора |
| `time_mode` | `"sync"` или `"realtime"` (см. «Режим реального времени») |
| `control_hz` | Шагов в секунду времени симулятора (по умолчанию 100): один `STEP` продвигает время на `1 / control_hz` |
| `time_limit` | Лимит времени попытки в секундах |
| `drone` | `class` (`"ai_mission"`: вупер организаторов; `"ai_core"`: свой дрон команды из ее файла), `name`, `calibrated` (false = временная модель вупера) |
| `rc` | `channels` (16), `rate_hz`, `latency_ms`, `failsafe_ms` |
| `sensors.camera` | `width`, `height`, `fps`, `format` (`"rgb8"`), `hfov_deg` (от края до края), `tilt_deg` (наклон вверх), `latency_ms`, параметры калибровки `fx`, `fy`, `cx`, `cy` в пикселях, `distortion` (`model: "radial_k1"`, `k1`), `mount` (положение в осях корпуса, метры) |
| `sensors.lidar` | `rate_hz`, `rays`, `min_m`, `max_m`, `angle_step_deg`. Нет ключа, если у дрона нет лидара |
| `sensors.imu` | `rate_hz`, `frame` |
| `sensors.tof` | `rate_hz`, `min_m`, `max_m`, `direction` (`"down"`) |
| `sensors.battery` | `rate_hz`, `cells` |

### START / RESET → OBSERVATION

Оба сообщения ставят дрон на стартовую площадку, обнуляют время симулятора и возвращают первое наблюдение с кадром
камеры, снятым в этот момент. У `START` пустой заголовок. `RESET` (тренировка) может нести `seed` (int): зерно шума
датчиков. В режиме соревнования `START` принимается один раз на соединение.

### STEP → OBSERVATION

Заголовок `STEP`: `rc`, массив не больше чем из 16 чисел, каналы пульта в микросекундах (от 1000 до 2000):

| Индекс | Канал | Что это |
|---|---|---|
| 0 | Roll | 1500 центр, 2000 = вправо |
| 1 | Pitch | 1500 центр, 2000 = вперед (нос вниз) |
| 2 | Throttle | 1000 = ноль, 2000 = полный газ |
| 3 | Yaw | 1500 центр, 2000 = вправо (по часовой стрелке, если смотреть сверху) |
| 4 | AUX1, арминг | выше 1500 = арминг включен. Полетный контроллер включает моторы, только когда канал поднимается **при газе не выше 1050** |
| 5 | AUX2, режим полета | ниже 1300 Angle (дрон сам держит горизонт), от 1300 до 1700 Horizon, выше 1700 Acro |
| 6–15 | запасные | не читаются |

Значения вне 1000–2000 обрезаются; недостающие каналы ставятся в центр (газ и AUX внизу). Массив, в котором есть
что-то кроме конечных чисел, отбрасывается целиком: для канала управления это потерянный пакет. `STEP` без `rc`
продвигает симуляцию без пакета (та же потеря пакета, но намеренная).

Симулятор пропускает пакет через модель канала управления (постоянная задержка `latency_ms`; если пакетов нет
`failsafe_ms`, моторы отключаются, пока AUX1 не выключат и не включат снова), продвигает симуляцию ровно на один шаг
управления с тем же полетным контроллером и той же моделью полета, на которых летает пилот-человек, и отвечает. Пока
попытка не идет, `STEP` ничего не меняет и возвращает текущее наблюдение.

### OBSERVATION

Заголовок:

| Ключ | Тип | Когда есть | Что это |
|---|---|---|---|
| `t` | float | всегда | Время симулятора от старта (с) |
| `tick` | int | всегда | Шагов физики от старта (1 кГц) |
| `running` | bool | всегда | False, когда попытка закончилась |
| `status` | str | всегда | `running` или причина конца: `finished`, `time_limit`, `stuck`, `disconnected` |
| `imu_n` | int | всегда | Число измерений IMU в данных |
| `tof` | словарь | когда есть новое измерение | `t`, `range` (м), `valid` (false вне диапазона; `range` тогда 0) |
| `battery` | словарь | когда есть новое измерение | `t`, `voltage` (В) |
| `lidar` | словарь | когда завершен полный оборот | `t` (конец оборота), `n` (лучей) |
| `camera` | словарь | когда есть новый кадр | `t` (когда кадр снят), `seq`, `size` (байт) |
| `truth` | словарь | тренировка, по запросу | `position` и `velocity` как [восток, север, вверх] в метрах, `points`, `score_time` |

Данные (`payload`), в таком порядке:

1. `imu_n` × 7 `float32`: `t, gx, gy, gz, ax, ay, az`.
2. Если есть `lidar`: `n` дальностей `float32` в метрах; 0 = ничего не измерено.
3. Если есть `camera`: `size` байт, `height` × `width` × 3, RGB, верхняя строка первой.

**Объектив камеры.** У картинки бочкообразное искажение. Пусть `x_d = (u - cx) / fx`, `y_d = (v - cy) / fy` и
`r² = x_d² + y_d²`. Тогда тангенсы истинных углов: `x_u = x_d (1 + k1 r²)`, `y_u = y_d (1 + k1 r²)`
(положительные направления: вправо и вниз). `k1 = 0` это обычная перспективная картинка.

**Видеоканал камеры.** Кадры проходят модель аналоговой видеосвязи: мягкие детали, размазанный и плывущий цвет,
шум, прыгающие строки и разорванные полосы. Чем дальше дрон от стартовой площадки (там стоит приемник) и чем больше
между ними препятствий, тем хуже картинка. Кроме того, камера подстраивает экспозицию под сцену.

**LiDAR.** 2D-сканер в горизонтальной плоскости самого дрона. Луч `k` смотрит на `k * angle_step_deg` от оси
«вперед», углы растут влево (против часовой стрелки, если смотреть сверху). Лучи одного оборота снимаются по очереди,
пока дрон движется, поэтому скан, снятый в полете, соответственно искривлен.

**Системы координат и оси.** Оси корпуса: x вперед, y влево, z вверх, правая тройка. Гироскоп в рад/с (x: крен
вправо +, y: нос вниз +, z: поворот влево +). Акселерометр в м/с², меряет кажущееся ускорение: в покое на ровном
полу он показывает (0, 0, +9,81).

**Время.** Все времена это время симулятора. Кадр камеры доходит до программы через `latency_ms` после съемки.
Датчики работают со своей частотой (по умолчанию камера 30 Гц, IMU 500 Гц, ToF 50 Гц, батарея 10 Гц), поэтому в
большинстве наблюдений есть только измерения IMU.

**Что никогда не отправляется в режиме соревнования:** координаты, скорость, ориентация, положения ворот, название
трассы, счет.

### DONE → OBSERVATION

Программа сообщает, что закончила. Попытка завершается статусом `finished`.

### PING → PONG (тренировка)

Заголовок `PING`: `payload` (int, не больше 4 МиБ). `PONG` возвращается с таким же числом байт. Нужно для измерения
транспорта.

### ERROR

Заголовок: `code` и `message`. Коды: `hello_first`, `protocol`, `token`, `not_allowed`, `already_started`,
`attempt_over`, `unknown_message`. После `ERROR` соединение закрывается.

## Режим соревнования

Один запуск симулятора это одна попытка. Программа должна подключиться и отправить `START` за `connect_timeout`
секунд (по умолчанию 60) и отвечать на каждое наблюдение за `step_timeout` секунд (по умолчанию 10) реального
времени; иначе попытка заканчивается статусом `timeout`. Если программа отключилась или ей отказано, попытка
заканчивается статусом `disconnected`. После попытки на `HELLO` приходит ответ `attempt_over`. Значения `status`,
которые может увидеть программа: `running`, `finished`, `time_limit`, `stuck`.

## Режим реального времени

Если в правилах `time_mode: "realtime"`, симулятор идет по настенным часам и никого не ждет. `STEP` тогда только
передает пакет в канал управления; `OBSERVATION` отправляется после каждого шага управления, просила программа или
нет. Программе следует читать все, что пришло, и действовать по самому новому наблюдению (в SDK это делают `step()`
и `latest()`). Программу, которая перестала читать, симулятор отключает, когда буфер отправки заполнен. Запуски в
режиме реального времени не повторяются точно; режим времени записывается в `result.json`.

## Детерминизм

Время симулятора идет только по `STEP`. Одна и та же сборка, трасса, зерно и последовательность сообщений `STEP`
дают один и тот же полет и один и тот же счет на компьютере того же типа, какой бы ни была скорость программы и
загрузка машины.
